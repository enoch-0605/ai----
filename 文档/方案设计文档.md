# 交互式 AI 闯关学习小程序方案设计文档

版本：V1.1  
日期：2026-09-11  
产品暂名：知关 AI / 智闯学堂

## 1. 项目定位

本项目是一款基于微信小程序的 AI 游戏化学习产品，将用户输入的任意知识主题转化为可交互的闯关题目，并在答题后提供即时解析和学习分析。

首期只验证核心闭环：

> 用户输入主题 → DeepSeek 生成题目 → 用户答题 → AI 判题与反馈 → 生成学习分析报告

已确认技术约束：

- 前端：Taro + React + TypeScript，首期编译为微信小程序。
- 后端：Python 3.11+ + FastAPI。
- AI 编排：LangChain。
- 数据库：MySQL 8.0+。
- 模型服务：DeepSeek API。
- 交付格式：Markdown。

## 2. MVP 范围

### 2.1 首期必须完成

- 首页输入学习主题。
- 选择题目数量（建议先固定 5 题，也可提供 5/10 两档）。
- 选择难度：入门、进阶、专家。
- 生成单选题和判断题。
- 动态难度调节：根据上一题答题结果生成下一题。
- 用户提交答案后展示正确性、解析和鼓励反馈。
- 完成闯关后生成总分、正确率、强项、弱项和学习建议。
- AI/网络异常时提供重试。
- 中断后可通过会话 ID 恢复当前闯关。

### 2.2 后续实现

登录、VIP、支付、联网搜索、AI 生图、语音、长文档 RAG、知识图谱、艾宾浩斯复习、好友 PK、排行榜、企业题库均不作为第一阶段阻塞项。

## 3. 用户流程与页面

```text
首页 → 输入主题与参数 → 创建会话 → 生成首题
→ 展示题目 → 提交答案 → 判题与反馈
→ 生成下一题 → 完成全部题目 → 分析报告
```

| 页面 | 主要职责 |
|---|---|
| 首页 | 主题输入、难度和题数配置、开始闯关 |
| 闯关页 | 题目、选项、进度、分数、生命值、反馈 |
| 结果页 | 总分、正确率、知识点掌握、错题摘要、建议 |
| 历史页 | MVP 可选，展示本地保存的最近会话 |

MVP 暂不实现开放式问答、多选题和语音答题。开放题的主观评分、上下文长度和争议处理成本较高，应在选择题闭环稳定后再加入。

## 4. 技术选型

### 4.1 前端方案对比

| 方案 | 优点 | 风险 | 结论 |
|---|---|---|---|
| 微信原生 | 微信 API 和调试适配最直接，性能与审核路径可控 | 后续跨端需要重写，工程复用能力较弱 | 备选 |
| Taro | React/TypeScript 工程体验好，组件和业务逻辑可复用，未来可扩展 H5/App | 编译层增加问题定位成本，微信新 API 可能存在适配时差 | **首选** |
| uni-app | Vue 生态和跨端发行能力强 | 首期引入的跨端抽象和插件依赖较多 | 不选 |

Taro 官方文档说明其支持微信小程序、H5、React Native 等目标；本项目首期只构建微信端，把多端能力作为未来选项，不在 MVP 中同步维护多端差异。

参考：[Taro 官方文档](https://docs.taro.zone/docs/)、[Taro 微信小程序构建文档](https://docs.taro.zone/docs/GETTING-STARTED)。

### 4.2 最终技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 小程序前端 | Taro 4.x + React + TypeScript | 页面、组件、状态和 API 调用 |
| 构建工具 | Taro CLI + 微信开发者工具 | 编译、预览、真机调试和上传 |
| 后端 API | Python 3.11+ + FastAPI + Uvicorn | REST API、异步请求、异常处理 |
| 数据校验 | Pydantic v2 | 请求、响应和 AI 对象校验 |
| AI 编排 | LangChain | Prompt、模型调用、结构化输出、重试和上下文 |
| 模型 | DeepSeek API | 题目、判题反馈和分析报告 |
| 数据库 | MySQL 8.0+ | 会话、题目、答题记录和报告 |
| ORM/迁移 | SQLAlchemy 2.x + Alembic | 数据访问、事务和版本迁移 |
| 缓存/限流 | Redis，可在 MVP 后接入 | 限流、短期缓存、异步任务辅助 |

### 4.3 DeepSeek 使用原则

DeepSeek API 采用 OpenAI 兼容格式，支持 Chat Completion、流式响应和 JSON 输出。模型 ID、价格和能力会变化，必须通过环境变量或配置中心管理，禁止把模型名和 API Key 写死在业务代码中。

参考：[DeepSeek API 官方文档](https://api-docs.deepseek.com/)。

小程序不能直连 DeepSeek。所有请求必须由 Python 后端代理，以保护密钥、统一限流、隐藏 Prompt、执行内容安全检查并保存业务状态。

## 5. 总体架构

```text
┌────────────────────────────────────┐
│ Taro + React 微信小程序             │
│ 首页 / 闯关页 / 结果页 / 本地缓存    │
└──────────────────┬─────────────────┘
                   │ HTTPS + JSON
┌──────────────────▼─────────────────┐
│ FastAPI API 层                      │
│ Pydantic 校验 / 限流 / 日志 / 错误码 │
└──────────────┬───────────┬─────────┘
               │           │
┌──────────────▼──────┐ ┌──▼──────────────┐
│ 闯关领域服务         │ │ LangChain AI 层  │
│ 会话/评分/状态/幂等  │ │ Prompt/解析/重试 │
└──────────────┬──────┘ └──┬──────────────┘
               │             │
       ┌───────▼───────┐ ┌───▼────────────┐
       │ MySQL + Redis │ │ DeepSeek API   │
       └───────────────┘ └────────────────┘
```

核心原则：LangChain 只负责 AI 调用编排，不能直接决定分数、生命值或数据库状态。会话状态机、计分、幂等和事务由 Python 领域服务负责。

## 6. 核心业务设计

### 6.1 会话状态机

```text
CREATED → GENERATING → PLAYING → SUBMITTING → FEEDBACK
                                      │             │
                                      └──重试───────┘
FEEDBACK → PLAYING（还有下一题）
FEEDBACK → COMPLETED（已完成）
任意状态 → FAILED / ABANDONED
```

每局保存 `sessionId`、当前题号、题目 ID、得分、生命值、难度、状态和生成版本。用户退出后重新进入，通过查询接口恢复，而不是从头生成。

### 6.2 动态难度

| 最近表现 | 下一题策略 |
|---|---|
| 连续答对 2 题 | 难度 +1，上限为专家 |
| 答错 1 题 | 保持难度，加强基础解释 |
| 连续答错 2 题 | 难度 -1，下限为入门 |
| 跳过题目 | 同难度生成知识点变体 |

AI 只能在服务端传入的知识点、题型和难度范围内出题，不能自由修改会话状态。

### 6.3 评分

- 单选/判断答对得 1 分，答错得 0 分。
- 答错后的纠错可记录，但不恢复首次得分。
- 掌握度综合正确率、难度、知识点覆盖和错误类型计算。
- 报告标注“AI 生成，仅供学习参考”。

## 7. LangChain 与 Prompt 设计

### 7.1 Chain 拆分

建立四条独立 Chain：

1. `OutlineChain`：把主题拆成可考查知识点。
2. `QuestionChain`：根据知识点、难度和历史表现生成下一题。
3. `EvaluationChain`：对答案进行判定并生成解析。
4. `ReportChain`：根据整局答题记录生成分析报告。

不建议一开始使用万能 Agent。独立 Chain 更容易测试、限额、观测、重试和更换模型。未来接入联网搜索时，再增加 Tool/Agent 层。

### 7.2 调用链

```text
业务参数
→ Pydantic 输入模型
→ LangChain PromptTemplate
→ DeepSeek Chat Model
→ Structured Output Parser / JSON Schema
→ 业务规则校验
→ MySQL 持久化
```

### 7.3 题目内部对象

```json
{
  "questionId": "q_001",
  "type": "single_choice",
  "knowledgePoint": "牛顿第二定律",
  "difficulty": "beginner",
  "stem": "题干内容",
  "options": [{"id": "A", "text": "选项内容"}],
  "answer": "A",
  "explanation": "解析内容",
  "wrongAnswerAnalysis": {"B": "错误原因"}
}
```

`answer` 只保留在后端内部对象中，前端 DTO 不得返回正确答案。所有模型响应必须经过 Pydantic/JSON Schema 校验；失败时降低随机性并重试一次，仍失败则返回 `AI_OUTPUT_INVALID`。

### 7.4 质量防线

- 必须存在唯一正确答案。
- 正确答案必须存在于选项中。
- 题干、选项和解析必须围绕同一知识点。
- 检查题目长度、重复率、敏感词和明显事实矛盾。
- 建立覆盖不同学科、难度和题型的离线评测集。

## 8. API 设计

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/sessions` | 创建会话并生成首题 |
| GET | `/api/v1/sessions/{id}` | 获取会话当前状态 |
| POST | `/api/v1/sessions/{id}/answers` | 提交答案、判题并生成下一题 |
| POST | `/api/v1/sessions/{id}/reports` | 生成或读取报告 |
| POST | `/api/v1/feedback` | 上报题目质量问题 |
| GET | `/api/v1/health` | 健康检查 |

创建请求示例：

```json
{
  "topic": "用 5 题了解量子力学基础",
  "questionCount": 5,
  "difficulty": "beginner",
  "questionTypes": ["single_choice", "true_false"]
}
```

提交答案请求示例：

```json
{
  "questionId": "q_001",
  "answer": "B",
  "clientRequestId": "uuid"
}
```

`clientRequestId` 用于幂等，防止用户重复点击造成重复计分或重复调用模型。

主要错误码：`INVALID_ARGUMENT`、`CONTENT_REJECTED`、`SESSION_NOT_FOUND`、`ANSWER_ALREADY_SUBMITTED`、`AI_TIMEOUT`、`AI_OUTPUT_INVALID`、`RATE_LIMITED`、`INTERNAL_ERROR`。

## 9. MySQL 数据设计

### 9.1 核心表

#### `game_session`

`id`、`anonymous_user_id`、`topic`、`difficulty`、`question_count`、`current_index`、`score`、`life`、`status`、`created_at`、`updated_at`

#### `question`

`id`、`session_id`、`question_index`、`type`、`knowledge_point`、`difficulty`、`public_content_json`、`private_answer_json`、`status`

#### `answer_record`

`id`、`session_id`、`question_id`、`answer`、`is_correct`、`response_ms`、`feedback_json`、`created_at`

#### `learning_report`

`session_id`、`summary`、`strengths`、`weaknesses`、`recommendations`、`report_json`、`created_at`

### 9.2 MySQL 实施规则

- 使用 InnoDB 和 `utf8mb4`。
- `question(session_id, question_index)` 建立唯一约束。
- `answer_record(session_id, question_id)` 建立唯一约束。
- `game_session(status, updated_at)` 建立组合索引。
- 需要统计和筛选的字段单独建列，JSON 仅保存结构化扩展内容。
- 提交答案在一个事务中完成：校验当前题 → 写答题记录 → 更新会话 → 决定下一题。
- 报告生成失败不回滚答题记录，报告可独立重试。

MVP 不做正式登录时，可生成随机匿名用户 ID；后续微信登录只绑定用户身份，不改变会话、题目和答题领域模型。

## 10. Taro 前端工程设计

建议目录：

```text
src/
├─ pages/
│  ├─ home/
│  ├─ game/
│  └─ report/
├─ components/
│  ├─ QuestionCard/
│  ├─ AnswerFeedback/
│  └─ ProgressBar/
├─ services/
│  └─ api.ts
├─ stores/
│  └─ game.ts
├─ types/
│  └─ api.ts
├─ utils/
│  ├─ request.ts
│  └─ storage.ts
└─ app.config.ts
```

- 使用 Taro 页面和组件，不在页面中直接拼接复杂业务逻辑。
- API 类型与后端 Pydantic 响应保持一致。
- 微信专属能力通过 Taro API；确需原生调用时使用 `process.env.TARO_ENV` 条件编译。
- 固定 Taro 版本、React 版本和微信开发者工具版本，避免编译器升级导致不可预期问题。
- 首期只执行 `taro build --type weapp`，使用微信开发者工具真机调试。

## 11. 微信专项设计

- 所有请求使用 HTTPS，API 域名加入小程序 request 合法域名。
- DeepSeek API 只在后端访问。
- MVP 采用完整 JSON 请求，不依赖流式输出。虽然 DeepSeek 支持流式响应，但结构化题目必须完整校验后才能落库，过早流式化会增加半截 JSON、重连和状态一致性风险。
- 生成中、提交中、失败和恢复状态必须在前端明确展示。
- 题目按题生成，避免一次加载整局大内容。
- 使用不可预测的会话 ID；分享功能开放后必须校验访问权限。

## 12. 安全与合规

- API Key 仅存放后端环境变量或密钥管理服务。
- 对主题、题目和模型输出执行内容安全检查。
- 对请求体长度、调用频率、单设备和单会话次数进行限制。
- 日志脱敏，不记录完整敏感输入、API Key 或完整 Prompt。
- 高风险主题（医疗、法律、金融等）默认拒绝或降级为非专业科普。
- 明确告知用户 AI 生成内容可能有误，仅供学习参考。
- 发布前准备隐私政策、用户协议、AI 生成说明、数据删除策略和反馈入口。

## 13. 开发流程

### 第 0 步：技术预研（1—2 天）

验证 DeepSeek API、FastAPI 测试接口、Taro 微信端请求、结构化输出和失败重试。

### 第 1 步：Taro 静态页面（2—3 天）

用 Mock 数据完成首页、闯关页、结果页和页面状态切换。

### 第 2 步：Python 后端领域服务（2—3 天）

使用 FastAPI、Pydantic、SQLAlchemy、Alembic 和 MySQL 完成会话、题目、答题和报告接口；先用 Mock AI 验证状态机、事务和幂等。

### 第 3 步：LangChain 接入 DeepSeek（3—5 天）

完成四条 Chain、Prompt、结构化解析、规则校验、超时、重试和调用指标。

### 第 4 步：联调和真机测试（3—4 天）

重点测试弱网、重复点击、切后台、退出重进、AI 超时、题目生成失败和报告重试。

### 第 5 步：小范围内测（3—5 天）

邀请 20—50 名用户，收集生成失败、题目质量、答题完成率、报告有用性和分享意愿。

## 14. 分阶段路线

### 阶段一：核心 MVP（2—3 周）

Taro 微信小程序、匿名会话、5 题闯关、单选/判断、动态难度、DeepSeek 出题判题、报告、重试、恢复和基础埋点。

### 阶段二：数据与商业化（3—4 周）

微信登录、历史记录、错题本、VIP、支付、复习计划和文本粘贴导入。

### 阶段三：高级 AI（3—4 周）

LangChain RAG、文档切片、向量检索、引用来源、联网搜索、异步生图、多导师和语音。

### 阶段四：社交与 B 端（3—4 周）

好友 PK、排行榜、战报海报、求助卡、企业题库、组织管理和数据看板。

## 15. 验收标准

### 功能

- 有效主题可以创建并完成 5 题闯关。
- 题目、选项和答题反馈展示正确。
- 重复提交不重复计分。
- 答题结果会影响分数、生命值或下一题难度。
- 完成后能得到结构完整的分析报告。
- AI/网络异常可以重试或恢复。

### 技术

- 小程序包中不存在 DeepSeek API Key。
- AI 输出全部经过结构化校验。
- 核心接口具备日志、耗时和错误指标。
- MySQL 事务和唯一约束能防止重复答题。
- Taro 项目可稳定编译到微信小程序，并能在真机完成全流程。

## 16. 风险与应对

| 风险 | 应对 |
|---|---|
| AI 题目事实错误 | Schema、规则校验、离线评测、人工抽检和用户反馈 |
| AI 响应慢 | 超时、重试、会话恢复，后续异步化 |
| JSON 格式不稳定 | Pydantic 校验、修复 Chain、失败降级 |
| 调用成本失控 | 匿名限流、题数限制、上下文摘要、成本监控 |
| Taro 与微信 API 适配问题 | 锁定版本、条件编译、微信开发者工具和真机回归 |
| 小程序审核风险 | 提前核对主体、类目、隐私、AI 内容和安全策略 |
| 文档版权和隐私风险 | RAG 后置，明确授权、保存期限和删除机制 |

## 17. 最终结论

推荐采用：

> Taro + React + TypeScript 微信小程序 + Python/FastAPI + LangChain + MySQL + DeepSeek API

首期只做稳定的 5 题动态闯关闭环。登录、支付、RAG、生图、联网、社交等能力在核心指标验证后分阶段接入。这样既满足未来扩展性，又将首期风险集中在最重要的三点：题目质量、答题体验和分析报告价值。
